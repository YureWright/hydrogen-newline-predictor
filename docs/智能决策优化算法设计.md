# 智能决策与优化算法设计

## 偏好驱动的「路线 · 车速 · 加氢/充电」联合优化

> **一句话**：把系统从"预测这趟要烧多少氢"，升级为"按你的**时间—费用偏好**，告诉你**走哪条路、开多快、在哪里加氢还是充电**，并在行驶中**动态重规划**"。

## 2. 为什么"加氢"和"充电"要一起规划

先看两个数字：

- **电池只有 155kWh**。纯电重卡通常 300~600kWh，所以这台车的电池只够跑很短一段（约 100~150km），**不能像电车那样只靠充电跑长途**。
- **两种补能的性格完全相反**：

| 补能方式 | 速度 | 价格（折算） | 适合场景 |
| --- | --- | --- | --- |
| 加氢 | 几分钟加满 | 约 35 元/kg，折合 **约 1.9 元/kWh** | 赶时间、长途主力 |
| 充电 | 155kWh 用 120kW 充约 **1.3 小时** | 约 **1.2 元/kWh**（含服务费） | 不赶时间、省成本 |

（折算依据：氢低热值 33.3 kWh/kg，电堆效率约 55%，即 1kg 氢约等于 18.3kWh 电。）

**结论**：加氢还是充电，本质上就是一道"**用时间换钱**"的题。用户越急，越倾向加氢；越在意成本，越倾向在合适的时候充电——这正好对应我们要提供的"时间—费用偏好滑杆"。

## 3. 优化问题定义

### 3.1 决策变量

| 变量 | 含义 |
| --- | --- |
| 路线 r | 从候选路线中选一条 |
| 车速 v(i) | 第 i 段建议车速 |
| 加氢量 Δh(i) | 在第 i 个站加多少氢（kg） |
| 充电量 Δe(i) | 在第 i 个站充多少电（kWh） |

### 3.2 目标函数

```
最小化广义总成本 J：

J = C_H2 + C_elec + C_toll + C_driver + C_other + λ × T
```

其中各符号含义见下表。

### 3.3 符号表

| 符号 | 含义 | 单位 / 取值 |
| --- | --- | --- |
| J | 广义总成本（越小越好） | 元 |
| C_H2 | 氢费 | 元 |
| C_elec | 电费 | 元 |
| C_toll | 过路费 | 元 |
| C_driver | 司机费 = 司机时薪 × 总时长 | 元 |
| C_other | 其他费用（轮胎/保养/保险摊薄） | 元 |
| λ | 时间价值（偏好参数） | 元/小时 |
| T | 总时长（行驶 + 补能） | 小时 |

**人话解释**：把所有要花的钱加起来，其中"时间"也折算成钱。λ 就是"你的一小时值多少钱"——拖动偏好滑杆，本质上就是在调 λ。

### 3.4 约束条件

| 类别 | 约束 |
| --- | --- |
| 道路 | 重卡限速、拥堵可通行速度、天气安全上限、坡度物理上限 |
| 车辆 | 氢罐容量上限、电池 SOC 上下限 |
| 补能 | 相邻加氢/充电站间距必须在续航范围内 |
| 司机 | 连续驾驶不超过 4 小时（可选） |

## 4. 算法架构

```
输入：起终点、出发时间、偏好 λ、车辆当前状态（剩余氢 / SOC / 位置）
        │
        ▼
┌──────────────────────────────────────────────┐
│ L0  偏好层：扫描 λ，生成「费用—时间」Pareto 前沿     │
│ L1  路线层：每条候选路线调用 L2 + L3，算出总成本 J    │
│ L2  速度层：逐段求「经济车速」v*                     │
│ L3  补能层：氢 + 电双资源 DP，决定在哪加/充、加/充多少 │
└──────────────────────────────────────────────┘
        │
        ▼
输出：推荐路线 + 分段车速 + 补能计划 + 司机指令
        │
        ▼
L4  动态重规划：每 5 分钟或事件触发，用最新状态重算，只执行「下一段」
```

---

## 5. 四层算法详解

### 5.1 L0 偏好层：给用户一条权衡曲线

把所有候选方案按「费用」和「时间」两个维度画在图上，只保留"没有其他方案能同时在两项上都更好"的点，得到一条 **Pareto 前沿**。

```
偏好加权形式：

J(α) = (1 - α) × 归一化费用 + α × 归一化时间       α ∈ [0, 1]
```

- α = 0：最省钱，慢一点也能接受
- α = 1：只求最快，钱不是问题
- 中间每个 α 都是一种折中方案

**人话**：不是给你一条路，而是给你一条曲线——"多花多少钱，能省多少时间"，你自己选。

### 5.2 L1 路线层：在候选路线里挑最优

对每条候选路线，先跑 L2（速度）和 L3（补能），得到该路线的最小总成本 J(r)，然后选成本最低的那条：

```
r* = 使 J(r) 最小的那条路线
```

**人话**：几条候选路线，每条都算"最省的开法 + 最省的补能"，谁总成本最低选谁。

> 工程上先用高德的 3 条候选（快、可靠）；后续可升级为 OSM 加权图上的 k 最短路，把氢耗、时间、安全做成边权，但不是第一优先级。

### 5.3 L2 速度层：每段"开多快最划算"

对固定路线的每一段，独立求解最优车速：

```
目标：最小化  m(v) × (L / 100) × p_H2  +  (c_driver + λ) × (L / v)

其中：
  m(v)     = 该速度下的百公里氢耗（kg/100km，由物理模型计算）
  L        = 该段里程（km）
  p_H2     = 氢价（元/kg）
  c_driver = 司机时薪（元/h）
  λ        = 时间价值（元/h）

约束： v_min ≤ v ≤ v_max
```

**为什么存在"甜点速度"？**

| 速度偏低 | 速度偏高 |
| --- | --- |
| 空调、气泵、水泵等附件功耗按时间摊到每公里上变多 | 风阻与速度平方成正比，功率与三次方成正比 |
| 单位里程氢耗高 | 单位里程氢耗急剧上升 |

所以中间一定存在一个**经济车速**（重卡常在 60~80 km/h）。

**怎么算**：速度从 20 到 100 km/h 逐点扫描（每 1 km/h 一个点），用**物理模型**算百公里氢耗，算总成本，取最小值。物理模型是公式推导、外推可靠；机器学习模型只在真实车速区间训练过，只做交叉校验。

**速度上限**（安全优先，取最小值）：

```
v_max = min( 重卡限速, 拥堵上限, 天气安全上限, 坡度物理上限 )
```

**解析近似**（用于向评委解释趋势）：若把氢耗近似为 m(v) = a + b·v²，则最优车速为：

```
v* = [ (c_driver + λ) / (2 · b · p_H2) ] ^ (1/3)
```

**人话结论**：时间越值钱（λ 越大），建议车速越高。

### 5.4 L3 补能层：氢 + 电双资源动态规划（DP）

车辆同时有两个"油箱"：

| 能量源 | 容量 | 特点 |
| --- | --- | --- |
| 氢罐 | 约 50~56 kg | 加氢快（几分钟），单价贵 |
| 电池 | 155 kWh | 充电便宜，但慢 |

```
DP 状态： (第 i 个站, 剩余氢量 h, 电池 SOC)

每站可选动作：
  1) 加氢 Δh  →  花费 Δh × p_H2
  2) 充电 Δe  →  花费 Δe × p_elec + 充电时间
  3) 直接走

转移成本：
  ΔC = Δh × p_H2
     + Δe × p_elec
     + (c_driver + λ) × ( Δe / P_charge + t_fix )

约束：
  0 ≤ h ≤ 氢罐容量
  SOC_min ≤ SOC ≤ SOC_max
  到下一站前剩余能量 ≥ 0
```

**人话**：就像手机"快充贵、慢充便宜"，车上是"加氢快、充电慢"。DP 帮你算清楚：**在哪些站加氢、哪些站顺手充电、每次加/充多少，才能在你的偏好下总成本最低。**

### 5.5 L4 动态重规划：边开边算，只执行下一步

核心思路：**算得远，但只执行下一步**（滚动时域 / MPC 思路）。

| 项目 | 规则 |
| --- | --- |
| 触发条件 | 每 5 分钟 / 拥堵变化 / 天气突变 / 偏离路线 / 氢量或电量异常 |
| 每次动作 | 用当前状态重算剩余行程，只执行"下一段"指令 |
| 防抖 | 新方案必须比当前方案省 3% 以上（或省 10 分钟以上）才切换 |

**给司机的指令示例**：

```
【下一段】G50 沪渝高速 · 建议 78 km/h
预计 1h20m 后到达 XX 服务区
补能建议：在 XX 服务区加氢 12kg（当前余量 18kg，够跑 210km）
提示：前方 15km 拥堵，已切换到备用路线（预计省 22 分钟）
```

## 6. 能量换算关系

```
能量守恒：
  E_need = E_H2 + E_bat

氢能转电：
  E_H2 = m_H2 × LHV × η_fc

  LHV  = 33.3 kWh/kg   （氢低热值）
  η_fc ≈ 0.55          （电堆系统效率）

即：1kg 氢 ≈ 18.3kWh 电

电池可用能量：
  E_bat = Q_bat × (SOC_max - SOC_min)
```

## 9. 风险与边界

| 风险 | 说明与对策 |
| --- | --- |
| 氢耗预测精度有限 | 新线路实测 R²≈0.4，优化定位为"相对比较"，不承诺绝对数值 |
| 速度外推 | 机器学习模型只在真实车速区间训练过，速度扫描限幅 30~90 km/h，以物理模型为主 |
| 补能数据时效 | 充电价格/功率、加氢站可用性可能变化，界面标注假设与数据时间 |
| 重规划抖动 | 加滞回阈值，避免路线频繁跳变 |
| 风阻系数差异 | 官网 0.27 与现有模型 0.35 不同，需按官网值校准 |

## 11. 本地启动方法

### 11.1 准备环境

- Node.js 18 以上（推荐 20+）
- Python 3.12

### 11.2 配置 .env

在项目根目录创建 `.env`，至少包含：

```
AMAP_KEY=你的高德Web服务Key
QWEATHER_KEY=你的和风天气Key
QWEATHER_HOST=你的和风天气Host
DEEPSEEK_API_KEY=你的DeepSeekKey
DEEPSEEK_BASE_URL=https://api.deepseek.com
DEEPSEEK_MODEL=deepseek-v4-flash
```

（`QWEATHER_*` 和 `DEEPSEEK_*` 为可选，不配则对应功能自动降级。）

### 11.3 安装依赖

```
npm install
python -m pip install -r ml/requirements.txt
```

Python 依赖版本需与 `ml/requirements.txt` 一致（scikit-learn 1.7.2），否则加载 `model.joblib` 会报 `No module named '_loss'`。

### 11.4 启动

**开发模式（推荐本地调试）**：

```
npm run dev
```

浏览器打开 http://localhost:5174

**生产模式**：

```
npm run build
node server.js
```

浏览器打开 http://localhost:5174

> `npm run dev` 启动 Vite 开发服务器（端口 5174），同时挂载 `/api` 中间件；`node server.js` 是生产服务，托管 `dist/` 静态文件并提供同一套 `/api`。
