## 二、为什么"加氢"和"充电"要一起规划

先看两个关键事实。

**事实一：电池相对较小。** 纯电重卡通常搭载 300~600 kWh 电池，而这台车只有 155 kWh，只够跑很短一段（约 100~150 km），**不能像电车那样只靠充电跑长途**。

**事实二：两种补能的性格完全相反。**

| 补能方式 | 速度 | 价格（折算） | 适合场景 |
|---|---|---|---|
| 加氢 | 几分钟加满 | 约 35 元/kg，折合约 1.9 元/kWh | 赶时间、长途主力 |
| 充电 | 155 kWh 用 120 kW 充约 1.3 小时 | 约 1.2 元/kWh（含服务费） | 不赶时间、省成本 |

折算关系为

$$1\ \mathrm{kg}\ \mathrm{H_2}\approx LHV\times\eta_{fc}=33.3\times0.55\approx18.3\ \mathrm{kWh}$$

其中 $LHV=33.3\ \mathrm{kWh/kg}$ 为氢的低热值，$\eta_{fc}\approx0.55$ 为电堆系统效率。

**结论**：加氢还是充电，本质上是一道"**用时间换钱**"的题。用户越急，越倾向加氢；越在意成本，越倾向在合适的时候充电。这正好对应我们要提供的"时间—费用偏好滑杆"。

但还有一条更硬的约束：**站得先有**。全国加氢站目前只有 571 座（本系统数据），其中 35MPa 536 座、35/70MPa 双压力 27 座、70MPa 8 座，价格约 30~32 元/kg；按 1°×1° 网格统计只覆盖 155 个网格。按站点间最近邻距离看，中位数 6km，但 P90 达到 61km、最大 360km——**很多路段几十公里内根本没有加氢站**。所以"加氢还是充电"不是纯经济问题，而是先由"沿途有什么站"决定的可行性问题。

## 三、优化问题定义

### 3.1 决策变量

| 变量 | 含义 | 单位 |
|---|---|---|
| $r$ | 选择哪条候选路线 | — |
| $v_i$ | 第 $i$ 段建议车速 | km/h |
| $\Delta h_i$ | 在第 $i$ 个站加多少氢 | kg |
| $\Delta e_i$ | 在第 $i$ 个站充多少电 | kWh |

### 3.2 目标函数

优化目标是最小化**广义总成本**：

$$J=C_{H_2}+C_{elec}+C_{toll}+C_{driver}+C_{other}+\lambda T$$

其中"时间"也被折算成钱：$\lambda$ 表示用户的时间价值（元/小时），拖动偏好滑杆本质上就是在调 $\lambda$。

### 3.3 符号表

| 符号 | 含义 | 单位或取值 |
|---|---|---|
| $J$ | 广义总成本 | 元 |
| $C_{H_2}$ | 氢费 | 元 |
| $C_{elec}$ | 电费 | 元 |
| $C_{toll}$ | 过路费 | 元 |
| $C_{driver}$ | 司机费 $=c_d\times T$ | 元 |
| $C_{other}$ | 其他费用（轮胎、保养、保险摊薄） | 元 |
| $\lambda$ | 时间价值（偏好参数） | 元/小时 |
| $T$ | 总时长（行驶 + 补能） | 小时 |
| $c_d$ | 司机时薪 | 约 60 元/小时 |

### 3.4 约束条件

| 类别 | 约束 |
|---|---|
| 道路 | 重卡限速、拥堵可通行速度、天气安全上限、坡度物理上限 |
| 车辆 | 氢罐容量上限、电池 SOC 上下限 |
| 补能 | 相邻补能站间距必须在续航范围内；站点类型（仅加氢 / 仅充电 / 两者都有）必须匹配 |
| 司机 | 连续驾驶不超过 4 小时（可选） |

## 四、算法架构

```
输入：起终点、出发时间、偏好 λ、车辆状态（剩余氢 / SOC / 位置）
        │
        ▼
┌──────────────────────────────────────────────┐
│ L0  偏好层：扫描 λ，生成「费用—时间」Pareto 前沿     │
│ L1  路线层：先做补能站覆盖可行性预检，再调用 L2 + L3    │
│ L2  速度层：逐段求「经济车速」v*                     │
│ L3  补能层：按站点类型做氢+电双资源 DP，决定在哪加、加多少│
└──────────────────────────────────────────────┘
        │
        ▼
输出：推荐路线 + 分段车速 + 补能计划 + 司机指令
        │
        ▼
L4  动态重规划：每 5 分钟或事件触发，用最新状态重算，
    但只执行「下一段」指令
```

## 五、四层算法详解

### 5.1 L0 偏好层：给用户一条权衡曲线

把所有候选方案按"费用"和"时间"两个维度画在图上，只保留"没有其他方案能同时在两项上都更优"的点，连成的曲线称为 **Pareto 前沿**。

为在不同偏好的方案之间做选择，用加权形式：

$$J_\alpha=(1-\alpha)\,\tilde{C}+\alpha\,\tilde{T},\qquad \alpha\in[0,1]$$

其中 $\tilde{C}$、$\tilde{T}$ 分别为归一化后的费用与时间。

- $\alpha=0$：最省钱，慢一点也能接受
- $\alpha=1$：只求最快，钱不是问题
- 中间每个 $\alpha$ 都对应一种折中方案

**人话**：不是给你一条路，而是给你一条曲线——"多花多少钱，能省多少时间"，让你自己选。

### 5.2 L1 路线层：在候选路线里挑最优

对每条候选路线，先跑 L2（速度）和 L3（补能），得到该路线的最小总成本 $J(r)$，再选成本最低者：

$$r^{*}=\underset{r}{\operatorname{argmin}}\ J(r)$$

**人话**：几条候选路线，每条都算"最省的开法 + 最省的补能"，谁总成本最低选谁。

**前置：路线可行性预检。** 在进入优化之前，先沿每条候选路线扫描补能站覆盖：如果存在一段"超过最大续航、且沿途没有任何可达站点"的区间，这条路线直接判为**不可行**（或计入绕行代价后重新评估），不进入后面的速度与补能优化。这一步把"加氢站有没有"变成了路线筛选的硬条件。

> 工程上先用高德的 3 条候选（快、可靠）；后续可升级为 OSM 加权图上的 $k$ 最短路，把氢耗、时间、安全做成边权，但不是第一优先级。

### 5.3 L2 速度层：每段"开多快最划算"

对固定路线的每一段，独立求解最优车速：

$$\min_{v}\ m(v)\cdot\frac{L}{100}\cdot p_{H_2}+(c_d+\lambda)\cdot\frac{L}{v}$$

约束为

$$v_{\min}\le v\le v_{\max}$$

$$v_{\max}=\min\left(v_{limit},\ v_{congestion},\ v_{weather},\ v_{grade}\right)$$

式中 $m(v)$ 为该车速下的百公里氢耗（kg/100km，由物理模型计算），$L$ 为段长（km），$p_{H_2}$ 为氢价（元/kg）。

**为什么存在"甜点速度"？**

| 速度偏低时 | 速度偏高时 |
|---|---|
| 空调、气泵、水泵等附件功耗按时间摊到每公里上变多 | 风阻与速度平方成正比，功率与速度三次方成正比 |
| 单位里程氢耗偏高 | 单位里程氢耗急剧上升 |

因此中间必然存在一个**经济车速**（重卡通常在 60~80 km/h）。

**怎么算**：使用确定性的分层搜索。第一层在完整可行区间内按 5 km/h 粗扫；第二层在粗扫最低点左右 5 km/h 内按 1 km/h 加密；第三层在最新最低点左右 1 km/h 内按 0.2 km/h 精修。每一层都用物理模型计算百公里氢耗与广义成本。这样既不假设成本函数处处光滑，也不需要遗传算法的随机搜索；物理模型负责外推，机器学习模型仅在真实速度区间内做交叉校验。

**解析近似**（用于解释趋势）：若把氢耗近似为

$$m(v)=a+bv^{2}$$

则最优车速满足

$$v^{*}=\left(\frac{c_d+\lambda}{2bp_{H_2}}\right)^{1/3}$$

**结论**：时间越值钱（$\lambda$ 越大），建议车速越高。

### 5.4 L3 补能层：氢 + 电双资源动态规划

车辆同时拥有两个"油箱"：

| 能量源 | 容量 | 特点 |
|---|---|---|
| 氢罐 | 约 50~56 kg | 加氢快（几分钟），单价贵 |
| 电池 | 155 kWh | 充电便宜，但慢 |

**先看站点类型。** 每个补能站先标注它能提供什么：仅加氢（35/70MPa）、仅充电、两者都有、或者都没有。**DP 的动作集合随站点类型变化**——加氢站只能加氢，充电站只能充电，两者都有才能选最优；站点不在路线上时，还要计入绕行距离与绕行时间。

以"站点序号、剩余氢量、电池 SOC"为状态做动态规划：

$$\text{状态}:\ (i,\ h,\ SOC)$$

$$\text{动作}:\ \text{加氢}\ \Delta h\ \big|\ \text{充电}\ \Delta e\ \big|\ \text{直接前往下一站}$$

单次转移成本为

$$\Delta C=\Delta h\,p_{H_2}+\Delta e\,p_{elec}+(c_d+\lambda)\left(\frac{\Delta e}{P_{charge}}+t_{fix}+t_{detour}\right)$$

其中 $t_{detour}$ 为绕行到站点的额外时间。

约束为

$$0\le h\le Q_{H_2},\qquad SOC_{\min}\le SOC\le SOC_{\max}$$

并要求相邻两个可用补能点之间的距离不超过当前能量可行驶的距离；否则该路径不可行。

**人话**：就像手机"快充贵、慢充便宜"，车上是"加氢快、充电慢"。动态规划帮你算清楚：在哪些站加氢、哪些站顺手充电、每次加或充多少，才能在你的偏好下总成本最低。

### 5.5 L4 动态重规划：边开边算，只执行下一步

核心思路是"算得远，但只执行下一步"，即滚动时域（MPC）思想。

| 项目 | 规则 |
|---|---|
| 触发条件 | 每 5 分钟；拥堵变化；天气突变；偏离路线；氢量或电量异常 |
| 每次动作 | 用当前状态重算剩余行程，只执行"下一段"指令 |
| 防抖机制 | 新方案必须比当前方案省 3% 以上（或省 10 分钟以上）才切换 |

给司机的指令示例：

```
【下一段】G50 沪渝高速 · 建议 78 km/h
预计 1h20m 后到达 XX 服务区
补能建议：在 XX 服务区加氢 12kg（当前余量 18kg，够跑 210km）
提示：前方 15km 拥堵，已切换到备用路线（预计省 22 分钟）
```

## 六、能量换算关系

规划时需要把氢和电换算到同一口径。能量守恒关系为

$$E_{need}=E_{H_2}+E_{bat}$$

氢能转电为

$$E_{H_2}=m_{H_2}\cdot LHV\cdot\eta_{fc}$$

电池可用能量为

$$E_{bat}=Q_{bat}\left(SOC_{\max}-SOC_{\min}\right)$$

其中 $LHV=33.3\ \mathrm{kWh/kg}$，$\eta_{fc}\approx0.55$，即

$$1\ \mathrm{kg}\ \mathrm{H_2}\approx18.3\ \mathrm{kWh}$$

## 九、风险与边界

| 风险 | 说明与对策 |
|---|---|
| 氢耗预测精度有限 | 新线路实测 $R^2\approx0.4$，优化定位为"相对比较"，不承诺绝对数值 |
| 速度外推 | 机器学习模型只在真实车速区间训练过；速度在道路重卡上限内按 5 → 1 → 0.2 km/h 分层搜索，以物理模型为主 |
| 补能数据时效 | 充电价格与功率、加氢站可用性可能变化，界面标注假设与数据时间 |
| 补能站覆盖不足 | 加氢站稀疏（P90 最近邻 61km），部分路线可能无站可用，必须做可行性预检并提示"需绕行"或"路线不可行" |
| 充电站数据上限 | 高德单城市最多返回 200 条（8 页×25），300 个城市已顶到上限；密集城区需用「周边检索（place/around）」沿路线补充 |
| 重规划抖动 | 加滞回阈值，避免路线频繁跳变 |
| 风阻系数差异 | 官网 0.27 与现有模型 0.35 不同，需按官网值校准 |

## 十一、本地启动方法

### 11.1 准备环境

- Node.js 18 以上（推荐 20 及以上）
- Python 3.12

### 11.2 配置 .env

在项目根目录创建 `.env`，至少包含：

```
AMAP_KEY=你的高德Web服务Key
QWEATHER_KEY=你的和风天气Key
QWEATHER_HOST=你的和风天气Host
DEEPSEEK_API_KEY=你的DeepSeekKey
DEEPSEEK_BASE_URL=https://api.deepseek.com
DEEPSEEK_MODEL=deepseek-v4-flash
```

其中 `QWEATHER_*` 与 `DEEPSEEK_*` 为可选，不配置则对应功能自动降级。

### 11.3 安装依赖

```
npm install
python -m pip install -r ml/requirements.txt
```

Python 依赖版本需与 `ml/requirements.txt` 保持一致（scikit-learn 1.7.2），否则加载 `model.joblib` 会报 `No module named '_loss'`。

### 11.4 启动

开发模式（推荐本地调试）：

```
npm run dev
```

生产模式：

```
npm run build
node server.js
```

两种方式都通过浏览器访问 http://localhost:5174

> `npm run dev` 启动 Vite 开发服务器（端口 5174），同时挂载 `/api` 中间件；`node server.js` 为生产服务，托管 `dist/` 静态文件并提供同一套 `/api`。
