## 1. 为什么要把"加氢"和"充电"放在一起规划（人话版）

先看两个数字：

- **电池只有 155kWh**。纯电重卡通常 300~600kWh，所以这台车的电池"只够跑很短一段"（约 100~150km），**不能像电车那样只靠充电跑长途**。
- **两种补能的性格完全相反**：

| 补能方式 | 速度 | 价格（折算） | 适合场景 |
| --- | --- | --- | --- |
| **加氢** | 几分钟加满 | 约 35 元/kg ≈ **1.9 元/kWh**（按 LHV 33.3 kWh/kg、效率 55% 折算） | 赶时间、长途主力 |
| **充电** | 155kWh 用 120kW 充约 **1.3 小时** | 约 **1.2 元/kWh**（含服务费，可按地区调） | 不赶时间、省成本 |

**所以"这次是加氢还是充电"本质上是一个"用时间换钱"的决策**——正好对应我们要给用户的"时间-费用偏好滑杆"。用户越急，就越倾向加氢；用户越在意成本，就越倾向在合适的时候充电。

## 2. 把需求翻译成数学问题

**决策变量**：

- 路线 $r$（从候选路线中选）
- 每段车速 $v_i$
- 补能方案：在哪个站、**加多少氢 $\Delta h$、充多少电 $\Delta e$**

**目标函数**（广义成本，越小越好）：

$$
J = \underbrace{C_{H_2}}_{\text{氢费}} + \underbrace{C_{elec}}_{\text{电费}} + \underbrace{C_{toll}}_{\text{过路费}} + \underbrace{c_d T}_{\text{司机费}} + \underbrace{c_o L}_{\text{其他}} + \underbrace{\lambda \cdot T}_{\text{时间成本}}
$$

**人话解释**：把所有要花的钱加起来，其中"时间"也折算成钱（$\lambda$ = 你每小时时间值多少钱）。用户拖偏好滑杆，本质上就是在调这个 $\lambda$。

**约束条件**：

- 道路限速、拥堵可通行速度、天气安全上限、坡度物理上限
- 氢罐容量、电池容量（SOC 上下限）
- 加氢站/充电站的间距必须能到达
- 司机连续驾驶时长（可选，4 小时强制休息）

## 3. 算法总架构：四层 + 滚动重规划

```
输入：起终点、出发时间、偏好λ、当前状态（剩余氢量 / SOC / 位置）
        │
        ▼
┌─────────────────────────────────────────────┐
│ L0 偏好层：把 λ 扫一遍 → Pareto 前沿（时间-费用权衡曲线）│
│ L1 路线层：每条候选路线 → L2 + L3 → 得到 J_r(λ)        │
│ L2 速度层：逐段求"经济车速" v_i*                        │
│ L3 补能层：氢+电双资源 DP，决定在哪加/充、加/充多少      │
└─────────────────────────────────────────────┘
        │ 选 J 最小的路线 r*
        ▼
输出：路线 + 分段车速 + 补能计划 + 司机指令
        │
        ▼
行驶中：每 Δt / 事件触发 → 用最新状态重跑 → 只执行"下一段"（L4 动态重规划）
```

---

## 4. 各层算法详解（含"人话版"解释）

### 4.1 L0 偏好层：给用户一条"权衡曲线"，而不是一条路

做法：把偏好参数 $\alpha$ 从 0 扫到 1，每个 $\alpha$ 解一次优化，得到一组 $(费用, 时间)$ 最优点：

$$
J_\alpha = (1-\alpha)\,\tilde{C} + \alpha\,\tilde{T}, \quad \alpha \in [0,1]
$$

（$\tilde C, \tilde T$ 是归一化后的费用和时间）

**人话**：$\alpha=0$ 是"最省钱、慢点也行"；$\alpha=1$ 是"只要最快、钱不是问题"。中间每一点都是一种折中。把这些点连起来，就得到一条 **Pareto 前沿**——**评委一眼就能看懂"多花多少钱能省多少时间"**。

---

### 4.2 L1 路线层：在候选路线里挑最优

对每条候选路线，跑一遍 L2（速度）+ L3（补能），得到该路线在给定偏好下的最小广义成本 $J_r(\lambda)$，然后：

$$
r^* = \arg\min_{r} J_r(\lambda)
$$

**人话**：几条候选路线，每条都算"最省的开法 + 最省的补能"，谁的总成本最低就选谁。

> 工程上先用高德的 3 条候选（快、可靠）；后续可升级为 OSM 加权图上的 k 最短路（把氢耗、时间、安全做成边权），但不是第一优先级。

---

### 4.3 L2 速度层：每段"开多快最划算"

对固定路线的每一段，独立求解：

$$
\min_{v}\ \underbrace{m_{H_2/100km}(v)\cdot \frac{L}{100}\cdot p_{H_2}}_{\text{氢费}} + \underbrace{(c_d+\lambda)\cdot\frac{L}{v}}_{\text{司机费 + 时间成本}}
$$

**为什么不是越快越好、也不是越慢越好？**

- 太慢：附件功耗（空调、气泵、水泵）按时间摊到每公里上变多，且频繁起停更费氢 → **单位里程氢耗高**
- 太快：风阻与速度平方成正比（功率与三次方成正比）→ **单位里程氢耗急剧上升**
- 所以中间一定存在一个"甜点速度"，这就是**经济车速**（重卡常在 60~80 km/h）

**怎么算**：把速度从 20 到 100 km/h 逐点扫描（每 1 km/h 一个点），用**物理模型**算该速度下的百公里氢耗，再算总成本，取最小值。物理模型是公式推导、外推可靠；机器学习模型只在真实车速区间训练过，只用来交叉校验。

**速度上限**（取最小值，安全优先）：

$$
v_{\max,i} = \min(\text{重卡限速},\ \text{拥堵上限},\ \text{天气安全上限},\ \text{坡度物理上限})
$$

**解析近似**（用于向评委解释）：若把氢耗近似为 $m(v)=a+bv^2$，最优车速满足

$$
v^* = \left(\frac{c_d+\lambda}{2b\,p_{H_2}}\right)^{1/3}
$$

**人话结论**：**时间越值钱（λ 越大），建议车速越高**——这个结论本身就能讲成一个卖点。

---

### 4.4 L3 补能层：氢 + 电双资源 DP（在哪加、加多少、充不充）

这是本设计最有意思的一层。车辆同时有**两个"油箱"**：

- 氢罐：容量 $Q_{H_2}$（如 50kg），加氢快、单价贵
- 电池：容量 $Q_{bat}$（如 155kWh），充电便宜、但慢

**DP 状态**：`(第 i 个站, 剩余氢量 h, 电池 SOC)`

**在每一站的动作（三选一或组合）**：

1. 加氢：加 $\Delta h$，花费 $\Delta h \cdot p_{H_2}$，耗时几分钟
2. 充电：充 $\Delta e$，花费 $\Delta e \cdot p_{elec}$，耗时 $\Delta e / P_{charge} + t_{固定}$
3. 直接走

**转移成本**：

$$
\Delta C = \Delta h \cdot p_{H_2} + \Delta e \cdot p_{elec} + (c_d+\lambda)\left(\frac{\Delta e}{P_{charge}} + t_{fix}\right)
$$

**约束**：$h \le Q_{H_2}$、$SOC \le SOC_{max}$、到下一站前剩余能量 $\ge 0$。

**人话**：就像手机有"快充贵、慢充便宜"，车上有"加氢快、充电慢"。DP 就是帮你算清楚：**在哪些站加氢、哪些站顺便充电、每次加/充多少，才能在你的偏好下总成本最低。**

**能量守恒（把氢和电换算到同一口径）**：

$$
E_{需求} = E_{氢} + E_{电},\qquad E_{氢} = m_{H_2}\cdot LHV \cdot \eta_{fc}
$$

（$LHV = 33.3\ \text{kWh/kg}$，$\eta_{fc}\approx 0.55$；即 1kg 氢约能变成 18.3kWh 的电）

---

### 4.5 L4 动态重规划：边开边算，只执行下一步

**核心思想**：算得远，但只执行下一步（类似"滚动时域/MPC"）。

- **触发条件**：每 5 分钟 / 拥堵等级变化 / 天气突变 / 偏离路线 / 氢量、电量异常
- **每次触发**：读取当前状态（位置、剩余氢、SOC、已用时间、最新路况天气）→ 以"当前位置→终点"为新的优化问题重跑 L1~L3 → **只执行"下一段"的指令**
- **防抖（关键）**：路线不能来回跳。新方案必须比当前方案**省 3% 以上**（或省 10 分钟以上）才切换，且切换本身要计入绕行代价

**给司机的输出（下一段指令卡）**：

```
【下一段】G50 沪渝高速 · 建议 78 km/h
预计 1h20m 后到达 XX 服务区
补能建议：在 XX 服务区加氢 12kg（当前余量 18kg，够跑 210km）
⚠️ 前方 15km 拥堵，已切换到备用路线（预计省 22 分钟）
```

## 6. 交互与展示设计

1. **偏好滑杆**：时间优先 ←→ 费用优先（实时重算，推荐点沿 Pareto 曲线滑动）
2. **Pareto 前沿图**：横轴总时间、纵轴总费用，每个点是一条"最优方案"，标出当前推荐
3. **路线卡片**：费用、时间、氢耗、过路费、补能计划一屏对比
4. **分段速度建议表**：段 / 道路 / 建议车速 / 氢耗 / 约束上限（限速·拥堵·天气）/ 预计到达
5. **补能计划**：在哪加氢/充电、加多少、单价、花费
6. **司机指令卡**：下一段怎么走、开多快、何时补能
7. **动态重规划演示**：模拟"前方拥堵/天气突变"，展示指令实时变化（评委最直观的演示点）

## 7. 风险与边界（必须提前说清）

1. **氢耗预测精度有限**：新线路实测 R²≈0.4，所以优化的定位是"**相对比较**"（哪条路更省、哪个速度更划算），不承诺绝对数值。
2. **速度外推**：机器学习模型只在真实车速区间训练过，速度扫描必须限幅（建议 30~90 km/h）并以物理模型为主。
3. **补能数据时效**：充电站价格/功率、加氢站可用性可能变化，界面必须标注假设与数据时间。
4. **重规划抖动**：必须加滞回阈值，否则演示时路线会"疯狂跳"。
5. **风阻系数差异**：官网 0.27 vs 现有模型 0.35，需按官网值校准（影响高速段氢耗约 10%+）。

## 9. 本地启动方法

```bash
cd hydrogen-newline-predictor

# 1) 准备 .env（放在项目根目录），至少包含：
#    AMAP_KEY=...            高德 Web服务 Key
#    QWEATHER_KEY=...        和风天气 Key（可选）
#    QWEATHER_HOST=...       和风天气 API Host（可选）
#    DEEPSEEK_API_KEY=...    AI 评估/推荐（可选）
#    DEEPSEEK_BASE_URL=https://api.deepseek.com
#    DEEPSEEK_MODEL=deepseek-v4-flash

# 2) 安装依赖
npm install
python -m pip install -r ml/requirements.txt

# 3) 开发模式（前端 + /api 中间件一起启动，推荐本地调试）
npm run dev
# 打开 http://localhost:5174

# 4) 或生产模式（先构建，再用 Node 起服务）
npm run build
node server.js
# 打开 http://localhost:5174
```

> 备注：`npm run dev` 用的是 Vite 开发服务器（`vite.config.ts` 里 `server.port = 5174`，同时挂载 `/api` 中间件）；`node server.js` 是生产服务，托管 `dist/` 静态文件 + 同一套 `/api`。Python 依赖版本需与 `ml/requirements.txt` 一致（scikit-learn 1.7.2，否则加载 `model.joblib` 会报 `No module named '_loss'`）。
